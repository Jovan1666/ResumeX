# 05 编辑器 UX 与本地存储调研

> 调研日期：2026-09-06

## 1. Zustand persist 自定义 storage 最小代码

### 1.1 官方类型形状（zustand 5.0.15 源码，逐字）

`StateStorage`（**字符串层**，供 `createJSONStorage` 使用）：

```ts
export interface StateStorage<R = unknown> {
  getItem: (name: string) => string | null | Promise<string | null>
  setItem: (name: string, value: string) => R
  removeItem: (name: string) => R
}
```

`PersistStorage`（**对象层**，`storage` 选项直接要求的类型）：

```ts
export type StorageValue<S> = {
  state: S
  version?: number
}

export interface PersistStorage<S, R = unknown> {
  getItem: (
    name: string,
  ) => StorageValue<S> | null | Promise<StorageValue<S> | null>
  setItem: (name: string, value: StorageValue<S>) => R
  removeItem: (name: string) => R
}
```

`createJSONStorage` 签名与语义（源码）：`getStorage: () => StateStorage<R>`，返回 `PersistStorage<S, unknown> | undefined`（getter 求值失败时返回 `undefined`，用于 SSR 环境）。它的实现就是把 `PersistStorage` 的 `value` 做 `JSON.stringify`（带可选 replacer），把 `getItem` 结果做 `JSON.parse`（带可选 reviver）。

**来源 URL：**
- https://raw.githubusercontent.com/pmndrs/zustand/main/src/middleware/persist.ts （类型与实现）
- https://zustand.docs.pmnd.rs/middlewares/persist （官方文档，2025 年迁移到 `/reference/middlewares/persist`，旧的 `/middlewares/persist` 路径已 404）

### 1.2 官方文档的关键警告（必须读）

> "`createJSONStorage` relies on `JSON.parse` and `JSON.stringify` and does not perform any runtime validation. The value read from storage is cast directly to your state type without checking its shape, so corrupt, stale, or tampered data will not be caught at runtime. For production use, implement a custom `PersistStorage` that validates the deserialized value — for example with a schema validation library such as Zod."

翻译：`createJSONStorage` 不做运行时校验。生产环境要么绕开它自己写 `PersistStorage`，要么在 `migrate`/手动 hydrate 入口做校验（项目现状是手动 `hydrate()` + `migratePersistedState()` 兜底校验，等价满足该警告）。

**来源 URL：** https://zustand.docs.pmnd.rs/reference/middlewares/persist （正文 Usage / Persisting a state with custom storage，Troubleshooting 一节也有同款警告：https://zustand.docs.pmnd.rs/reference/middlewares/persist#usage ）

### 1.3 createJSONStorage + idb-keyval 最小代码（可直接粘贴）

`idb-keyval` 的 API 签名（v6.3.0，README + 源码核对）：

```ts
get<T = any>(key: IDBValidKey, customStore = defaultGetStore()): Promise<T | undefined>  // 无 key 时 resolve undefined
set(key: IDBValidKey, value: any, customStore = defaultGetStore()): Promise<void>
del(key: IDBValidKey, customStore = defaultGetStore()): Promise<void>
createStore(dbName: string, storeName: string): UseStore
```

要点：
- `get` 找不到 key 时返回 `undefined`（不是 null，也不是 reject）—— 自定义 storage 需要转成 `null`。
- `set`/`del` 返回 `Promise<void>`，**配额不足时 reject（`QuotaExceededError` DOMException）**——不能吞，必须让它传到 persist 的错误回调。
- `createStore` 显式建库避免默认 `keyval-store` 与第三方冲突；同一个 `customStore` 实例给 JSON 和 Blob 复用同一库（项目现状即如此：`resumex-db`）。

```ts
// storage-idb.ts —— 直接可用（zustand 5 + idb-keyval 6，React 18 无依赖）
import { create } from 'zustand';
import { persist, createJSONStorage, type StateStorage } from 'zustand/middleware';
import { get, set, del, createStore, type UseStore } from 'idb-keyval';

const DB_NAME = 'resumex-db';
const STORE_NAME = 'resumex-state';

export const idbStore: UseStore = createStore(DB_NAME, STORE_NAME);

// —— StateStorage 形状：值必须是 string（createJSONStorage 会 JSON.stringify）——
const idbStateStorage: StateStorage = {
  getItem: async (name) => {
    const v = await get<string>(name, idbStore);
    return v ?? null; // idb-keyval 的 undefined 必须转 null
  },
  setItem: async (name, value) => {
    await set(name, value, idbStore); // 配额不足会 reject → 由 persist 的 onError 捕获
  },
  removeItem: async (name) => {
    await del(name, idbStore);
  },
};

// —— createJSONStorage 包装：把 StateStorage(string) 变成 PersistStorage(StorageValue) ——
const storage = createJSONStorage(() => idbStateStorage);

export const useStore = create<{ count: number; inc: () => void }>()(
  persist(
    (setState) => ({
      count: 0,
      inc: () => setState((s) => ({ count: s.count + 1 })),
    }),
    {
      name: 'resumex-state',
      version: 3,
      storage,
      partialize: (s) => ({ count: s.count }), // 不持久化函数
      onRehydrateStorage: () => (state, error) => {
        // state: 水合后的 state；error: 读取/解析/migrate 出错时传入
        if (error) console.error('[persist] hydrate 失败', error);
      },
      migrate: (persisted, version) => persisted as { count: number }, // 版本不符时调用
    },
  ),
);
```

**注意**：`setItem` 中 `await` 的拒绝会被 persist 处理并传给 `onRehydrateStorage` 返回的 post-rehydration 回调？—— 不，官方语义是：写失败在 `storage.setItem` reject 时，persist 内部会捕获并调用 `onError`（即 `onRehydrateStorage` 返回函数的 `error` 参数）+ 在 useEffect 里 `console.error`。**想要 UI 提示，标准做法是像项目现状那样在自定义 `setItem` 里自己 try/catch 并 `setState({ saveStatus: 'error' })`，或在 `onRehydrateStorage` 的 post 回调里读 error**。

**来源 URL：**
- https://github.com/jakearchibald/idb-keyval （README：`set`/`get`/`del` 返回 Promise、`get` 缺失返回 undefined、可存 structured-cloneable 值）
- https://github.com/jakearchibald/idb-keyval/blob/main/src/index.ts （源码签名：`get<T = any>(key: IDBValidKey, customStore = defaultGetStore()): Promise<T | undefined>`、`set(key, value, customStore): Promise<void>`、`del(key, customStore): Promise<void>`、`createStore(dbName, storeName): UseStore`）
- https://zustand.docs.pmnd.rs/reference/middlewares/persist （`createJSONStorage`、`PersistStorage`、`onRehydrateStorage`、`version`/`migrate`/`partialize`）
- https://www.npmjs.com/package/idb-keyval （当前版本 6.3.0）
- https://www.npmjs.com/package/zustand （当前版本 5.0.15）

### 1.4 不用 createJSONStorage 的等价格式（官方推荐生产级）

如果你想要完全控制反序列化校验，直接实现 `PersistStorage`（对象层，值就是 `{ state, version }`）：

```ts
const fullControlStorage: PersistStorage<{ count: number }> = {
  getItem: async (name) => {
    const v = await get(name, idbStore);
    if (v == null) return null;
    // 自己解析+校验（Zod 等），坏了就返回 null 而不是抛
    return JSON.parse(String(v)) as StorageValue<{ count: number }>;
  },
  setItem: async (name, value) => {
    await set(name, JSON.stringify(value), idbStore);
  },
  removeItem: async (name) => {
    await del(name, idbStore);
  },
};
```

项目现状走的是「`createJSONStorage` + 手动 hydrate 校验」，够用；但 §1.2 的警告意味着**任何从外部导入的备份数据（importBackup）都必须走 `parseStoredState` 式校验**（项目已做）。

## 2. IndexedDB 配额与 QuotaExceededError

### 2.1 配额没有固定数字，且远大于 localStorage

- **localStorage**：官方（web.dev）表述 "It is limited to about 5MB and can contain only strings."（web.dev 的「Avoid LocalStorage」章节措辞）。MDN 不写死数字，只声明 `QuotaExceededError` 语义：storage 满了就抛；「some browsers might give us an empty localStorage object with a quota of zero」。
- **IndexedDB**：配额由浏览器按「磁盘总量」计算，没有固定值，**每 origin 一个配额**：
  - Chrome/Edge：origin 最多可用**总磁盘的 60%**（persistent 与 best-effort 相同）；隐身模式约 5%；开启「关闭窗口时清除 cookie 和站点数据」时上限约 300MB。
  - Firefox：best-effort = min(磁盘 10%, 10 GiB)；持久化 = 磁盘 50% 且上限 8 TiB。
  - Safari：浏览器 app 约磁盘 60%，嵌入 WebView 约 15%；老版本初始 1 GiB，用完后弹窗请求扩容（每次 +200MB）。
- 配额是基于磁盘**总大小**计算的，不是可用空间（防指纹）："it is calculated based on the hard drive total size, not the currently available disk space"。

**结论：简历 JSON（几 KB~几百 KB）完全不用担心配额；照片按规格裁到 ≤150KB 单张，即使 20 张照片也只有 3MB，IndexedDB 绰绰有余 —— 配额问题是「用户头像多/未来功能扩容」时的事，但要保证错误路径存在。**

### 2.2 QuotaExceededError 怎么检测

三种信号，写法都基于 `DOMException.name`：

1. **尝试写时 catch**（最可靠，最终防线）：

```ts
try {
  await set(key, value, idbStore);
} catch (e) {
  // e 是 DOMException，name === 'QuotaExceededError'
}
```

web.dev 原文："Both IndexedDB and the Cache API throw a DOMError named QuotaExceededError when you've exceeded the quota available."（IndexedDB 场景：事务 `onabort` 触发，`event.target.error` 是 DOMException，检查 `error.name`）。

2. **写前 estimate 预检**（辅助，不是银弹）：

```ts
const { usage, quota } = await navigator.storage.estimate();
// usage: 已用字节；quota: 最大可用字节
// 注意：官方说明只返回"估算"值；Chrome 总是报 60% 磁盘，与实际自由空间无关
```

3. **`storage.persist()`**：请求持久化配额（防止 LRU 驱逐），返回 boolean。用来**避免**「数据被浏览器清掉」而不是避免配额超限。

### 2.3 怎么抛到 UI（项目现状 = 标准做法）

持久化失败必须是**上行**的（不静默、不 console-only）。官方 doc 也建议写存储都要 try/catch（MDN：Web developers should wrap JavaScript that writes to browser storage within try...catch blocks）。

项目 `storageAdapter.setItem` 的 try/catch + `saveStatus: 'error'`（`界面/src/app/store/useResumeStore.ts`）就是推荐形态：

```ts
setItem: async (_name, value) => {
  if (!_hydrated) return; // 水合门闩
  try {
    const parsed = JSON.parse(value) as { state: PersistedState };
    await resumeStorage.save(parsed.state);
    _lastSaveError = null;
    useResumeStore.setState({ saveStatus: 'saved' });
  } catch (e) {
    _lastSaveError = isQuotaError(e)
      ? '保存失败：存储空间不足，请导出备份'
      : `保存失败：${String((e as Error)?.message ?? e)}`;
    useResumeStore.setState({ saveStatus: 'error' });
  }
},
```

`isQuotaError` 判定宽严度（`界面/src/app/store/storage.ts`）：

```ts
export function isQuotaError(e: unknown): boolean {
  const name = (e as { name?: string })?.name || '';
  const msg = String((e as { message?: string })?.message || e || '');
  return (
    name === 'QuotaExceededError' ||
    name === 'QuotaExceeded' ||
    /quota/i.test(msg) ||
    /exceed/i.test(msg)
  );
}
```

**结论**：`QuotaExceededError` 是唯一要特殊映射的 DOMException；其余错误按通用「保存失败：<message>」上浮。判定用 `name` 为主、`message` 匹配为辅（兼容旧实现里 name 可能是 `QuotaExceeded` 的历史差异）。

**来源 URL：**
- https://web.dev/articles/storage-for-the-web （5MB、60%/80%、estimate、QuotaExceededError、eviction、persist）
- https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria （按浏览器列出的配额数字、"fails with a QuotaExceededError exception"、try..catch 建议、estimate 仅估算）

## 3. 照片 Blob 与 JSON 分离

### 3.1 值类型限制：哪些能进 IndexedDB

- IndexedDB 值 = 「能结构化克隆的任何东西」。MDN Basic Concepts："Each record has a value, which could include anything that can be expressed in JavaScript, including boolean, number, string, date, object, array, regexp, undefined, and null." 且明确：「Blobs and files can be stored」。
- **File 是 Blob 的子类**，所以 `File` 也能直接 `put` 进 IndexedDB（idb-keyval README：可以存 anything structured-clonable (numbers, arrays, objects, dates, **blobs** etc)）。
- **localStorage 只能存字符串**（web.dev："can contain only strings"）——这就是「照片必须从 JSON 里拆出去」的根本原因：dataURL 是字符串，一张 5MB 照片 base64 后 ~6.7MB，直接超 localStorage，也污染 JSON 可读性。

### 3.2 推荐做法：JSON 只存引用 key，Blob 用 idb-keyval 单独 key

项目 `avatar.ts` 的形态就是标准答案（Blob 直存 + key 引用）：

```ts
import { get, set, del } from 'idb-keyval';
import { customStore } from './storage'; // createStore('resumex-db', 'resumex-state') 的实例

const AVATAR_PREFIX = 'idb:avatar:';

export function avatarKeyFor(resumeId: string): string {
  return `${AVATAR_PREFIX}${resumeId}`;
}

export async function saveAvatar(resumeId: string, blob: Blob): Promise<string> {
  const key = avatarKeyFor(resumeId);
  await set(key, blob, customStore);        // Blob 直接存，不 base64，不转字符串
  return key;
}

export async function loadAvatar(key: string): Promise<Blob | null> {
  if (!key.startsWith(AVATAR_PREFIX)) return null;
  const blob = await get<Blob>(key, customStore);
  return blob instanceof Blob ? blob : null; // 防御：value 类型校验
}

export async function deleteAvatar(key: string): Promise<void> {
  if (!key.startsWith(AVATAR_PREFIX)) return;
  await del(key, customStore);
}
```

原则：
- `profile.avatar` 只存 `idb:avatar:<resumeId>` 字符串（几十字节）。
- **禁止** dataURL 进 JSON；项目迁移规则：`>20KB` 的旧 dataURL 直接丢弃并提示重传（设计意图：避免 200 字节约 20KB+ 的引用换 20KB 本地值）。
- 复制/删除简历必须 clone/delete Blob（规格 6.4 已列）。
- 备份（exportBackup/importBackup）：zip 里 `state.json` + `avatars/<resumeId>.jpg` 分离，不是把 Blob 塞 JSON。

**上浮要求**：`saveAvatar` reject（配额不足）同样要能被 UI 捕获 —— `set` 失败自然 reject，调用处（上传/裁切回调）加 try/catch 显示 toast。

### 3.3 URL.createObjectURL 生命周期（模板渲染照片的必守规则）

- `URL.createObjectURL(object)` 接受 **`Blob`（如 `File`）或 `MediaSource`**，返回 `blob:` 字符串。
- **生命周期语义（File API spec 原文）**：
  - "As long as the mapping exist the Blob can't be garbage collected, so some care must be taken to revoke the URL as soon as the reference is no longer needed."
  - "All URLs are revoked when the global that created the URL itself goes away."（即页面 unload/刷新时自动全部失效，blob URL 不能跨页面存活）
  - "Revocation of a blob URL decouples the blob URL from the resource it refers to, and if it is dereferenced after it is revoked, user agents must act as if a network error has occurred."（revoke 后再用 = 网络错误）
- **结论与规则**：
  1. `blob:` URL **不能**持久化到 JSON/localStorage —— 刷新后必然失效。模板渲染必须「每次用 Blob 现场 `createObjectURL`」。
  2. 每次 createObjectURL 都会把 Blob 钉在内存直到 revoke —— **组件卸载必须 revoke**（spec 已明确 `useObjectURL` 的 hook 语义）。
  3. 已有事实：`createAvatarObjectUrl` 类 hook 应在 `useEffect(() => { const url = URL.createObjectURL(blob); return () => URL.revokeObjectURL(url); }, [blob])` 中创建与回收。

- https://github.com/jakearchibald/idb-keyval （README：anything structured-clonable、get 缺失返回 undefined、set 返回 Promise）

## 4. React composition 事件序列与中文输入法防抖

### 4.1 规范事件序列（UI Events 3.6，逐字）

- 一个组合会话 = **`compositionstart` → 一个或多个 `compositionupdate` → `compositionend`**："a composition session consists of one compositionstart event, one or more compositionupdate events, and one compositionend event"。
- **during composition 的 input/beforeinput 序列**（§3.6.6）：`beforeinput` → `compositionupdate` → **`input`**。即：**组合过程中每次 DOM 更新都会触发 `input` 事件**（"The beforeinput and input events are sent along with the compositionupdate event whenever the DOM is updated as part of the composition"）。
- **compositionend 本身不带 input**："Since there are no DOM updates associated with the compositionend event, beforeinput and input events should not be sent at that time."
- `InputEvent.isComposing`："true if the input event occurs as part of a composition session, i.e., after a compositionstart event and before the corresponding compositionend event."
- 关键事件（keydown/compositionstart 前）：initiating keydown 的 `isComposing = false`。

**结论：input/onChange 在拼音组合的每一步（字母中间态）都会触发** —— 这是「中文输入时 store 里短暂出现拼音/候选串、被打断时状态残留」的根因。

### 4.2 React 侧事实

- react.dev 明确：`onChange` **behaves like the browser `input` event**（Fires immediately when the input's value is changed by the user；fires on every keystroke）。所以 React 受控输入的 `onChange` 同样在 composition 期间高频触发。
- React 官方文档**没有**专门说明 IME/`isComposing` 的 onChange 处理；`ChangeEventPlugin` 源码（`react-dom-bindings/src/events/plugins/ChangeEventPlugin.js`）对 text input 监听 `input` 事件后调 `updateValueIfChanged` 判断值变化后触发 `onChange` —— **没有 isComposing 过滤**。即：React 18 的 `onChange` 在 composition 期间照常触发。
- React issue #3926（中文拼音输入法触发过多 render / 期望确认后再触发）是最早的报告；**至今没有在 React 层内建 IME 节流**（官方从设计上不吞 input 事件，避免误解为浏览器行为差异）。合理对策在应用层。

### 4.3 防抖策略（应用层，三段式）

项目 `DebouncedInput` 已有 300ms debounce + blur 立即提交 + unmount flush + undo/redo 外部值覆盖保护 —— 但缺 composition 段。补法：**composition 期间只更新本地值，到 `compositionEnd` 才重置 debounce 计时**（避免拼音中间态进 store），concretely：

```tsx
// DebouncedInput 需要的三个增量（React 18，可直接并入现有组件）
const composingRef = useRef(false);

const handleCompositionStart = () => { composingRef.current = true; };

const handleCompositionEnd = (e: React.CompositionEvent<HTMLInputElement>) => {
  composingRef.current = false;
  // 候选确认后 value 已经通过 onChange 进入 localValue；
  // 只重置 debounce 计时，保证「组合结束后 300ms」才提交（避免组合尾部长输入连续推迟）
  if (timerRef.current) clearTimeout(timerRef.current);
  timerRef.current = setTimeout(() => {
    onChangeRef.current(e.currentTarget.value);
    isTypingRef.current = false;
  }, delay);
};

const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
  const newValue = e.target.value;
  setLocalValue(newValue);
  if (composingRef.current) return; // 组合中：只进 local，不启动 debounce
  isTypingRef.current = true;
  if (timerRef.current) clearTimeout(timerRef.current);
  timerRef.current = setTimeout(() => {
    onChange(newValue);
    isTypingRef.current = false;
  }, delay);
};

// JSX：
<input
  {...props}
  value={localValue}
  onChange={handleChange}
  onCompositionStart={handleCompositionStart}
  onCompositionEnd={handleCompositionEnd}
  onBlur={handleBlur}
/>
```

配套规则：
1. **compositionEnd 要强制 flush 一次定时器**（如上）：保证「组合结束后 300ms 内无后续输入才写 store」，同时防「失焦+组合中」丢字（现有 `onBlur` 已覆盖）。
2. **失焦/卸载时即使正在 composition 也要提交**（保留现有 blur/unmount flush，把 `composingRef` 一并清掉）。
3. **undo/redo 外部值同步**（现有 `useEffect([externalValue])` 清 `isTypingRef` 的竞争处理）保持不变，但要在清 pending timer 时**同时记 `externalValue` 为最新**，避免 compositionEnd 的 `onChangeRef.current(e.currentTarget.value)` 用旧 local 值回写覆盖 undo —— 现有代码的 `localValueRef/externalValueRef` 模式已经够用，补 composition 时**不要**在 compositionEnd 里无条件 flush store。
4. 更简单但不够好的替代方案：`onCompositionStart` 里直接 `blur` 或提示「请先按空格确认」——**不推荐**，UX 断裂。
5. 兜底方案（如果以上嫌重）：在 debounce 回调 `onChange(newValue)` 前检查 `composingRef.current === false`，组合中不提交、compositionEnd 时再补一次 —— 等价效果，但注意 compositionEnd 时 `e.currentTarget.value` 与最后一帧 onChange 的 value 一致，不需要额外 state。

**结论**：React 18 下最稳的 IME 处理 = 「本地值照常更新（保证拼音候选可见）+ composition 期间不启动/不触发 store 写入 + compositionEnd 重置 debounce」。项目只有 6 个字段输入量级且笔画少，不建议引入 `useDeferredValue`/requestIdleCallback 复杂化。

- https://developer.mozilla.org/en-US/docs/Web/API/InputEvent/isComposing （"if the event is fired after compositionstart and before compositionend"）
- https://react.dev/reference/react-dom/components/input （`onChange` "Behaves like the browser input event"；"Fires immediately when the input's value is changed by the user...fires on every keystroke"）

## 5. Electron `userData` 与备份文件

### 5.1 位置与路径（官方 docs 原文核对）

- `app.getPath('appData')`："Per-user application data directory, which by default points to: **`%APPDATA%` on Windows** / `$XDG_CONFIG_HOME` or `~/.config` on Linux / `~/Library/Application Support` on macOS"。
- `app.getPath('userData')`："The directory for storing your app's configuration files, which by default is the `appData` directory appended with your app's name. By convention files storing user data should be written to this directory..."。
- 结论：**Windows 默认 `userData` = `%APPDATA%\<AppName>`**，即 `C:\Users\<用户名>\AppData\Roaming\<AppName>`（AppName 为 `package.json` 的 `productName`/`name`，例如 ResumeX）。

### 5.2 是否适合放备份文件？（官方原文 = 两个「不推荐」+ 一个「推荐」）

- **不推荐写大文件**："it is not recommended to write large files here because some environments may backup this directory to cloud storage"（某些环境会把这目录同步到云端 —— 备份文件再备份一遍，且可能被云同步节流/冲突）。
- **推荐建子目录**："It is recommended to store app-specific files within a subdirectory of `userData` (e.g., `path.join(app.getPath('userData'), 'my-app-data')`) rather than directly in `userData` itself, to avoid naming conflicts with Chromium's own subdirectories (such as `Cache`, `GPUCache`, and `Local Storage`)"。
- 为什么**不要**直接放 `userData` 根：Chromium 的 `sessionData` 默认也指向 `userData`（"Chromium may write very large disk cache here"）。
- `app.getPath` 失败时 **throws an Error**（不是返回空串）—— 需要 try/catch 兜底。

**结论**：备份文件放 `path.join(app.getPath('userData'), 'backups')` 子目录（规格 §7 已这么写），单文件几百 KB ~ 几 MB，符合「不大 + 子目录」两条官方建议。**不要**放 `appData` 根、`exe` 同目录（安装目录可能被 NSIS 覆盖更新）或 `documents`（若配置了 OneDrive 同步同样有云同步冲突问题，但那是用户显式选择）。

### 5.3 Electron 渲染进程里 IndexedDB 就是 Chromium 的 IndexedDB

- Electron `userData` 下 Chromium 的 `Local Storage`/`IndexedDB` 目录（对应 `sessionData` 默认值）与浏览器 Web 版应用**不是同一个 origin**（`file://` 或自定 protocol），**不会共享数据**；NSIS 覆盖安装不会碰 IndexedDB（在 userData 里，不是安装目录）——规格里「不要把简历只放在安装目录」的依据就是这一点。
- `file://` 下 IndexedDB 可用性：规范层面 `file:` URL 的 localStorage 行为 "are undefined and may vary among different browsers"（MDN），但 Chromium/Electron 对 `file://` 的 IndexedDB 实际可用（项目 `idbAvailable()` 有兜底判断，若不可用走错误提示而不是静默）。

**来源 URL：**
- https://www.electronjs.org/docs/latest/api/app （getPath 全文；appData `%APPDATA%`；userData "appData directory appended with your app's name"；"not recommended to write large files here"；子目录建议；"throws an Error"）
- https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage （`file:` URL 的 localStorage 要求未定义）
- https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Basic_Concepts_Behind_IndexedDB （IndexedDB 值：structured clone）

## 6. Web 与 Electron 共用存储接口草图

目标：一套 `ResumeStorage` 接口，两种运行时就换「传输层」（Web = idb-keyval；Electron = idb-keyval + fs 备份目录），persist 配置不变。规格 §7 定义的行为已在此展开为可粘贴代码。

### 6.1 接口（与规格 02 §7 对齐）

```ts
export interface ResumeStorage {
  load(): Promise<PersistedState | null>;                 // hydrate；失败返回 null（不给演示数据）
  save(state: PersistedState): Promise<void>;             // 失败必须 throw（配额/写入）
  exportBackup(): Promise<Blob>;                          // Web: 下载；Electron: 写 userData/backups/ 并返回 Blob
  importBackup(file: File): Promise<{ success: boolean; message: string }>;
}

export interface PersistedState {
  resumes: Record<string, ResumeData>;
  activeResumeId: string;
  [key: string]: unknown;
}
```

### 6.2 分层图

```
useResumeStore (zustand persist)
   │ storage: createJSONStorage(() => adapter)     ← §1.3 形状
   ▼
storageAdapter (StateStorage: async setItem/removeItem，getItem=null 手动 hydrate)
   │                                  │
   ▼                                  ▼
createResumeStorage() (ResumeStorage)        avatar.ts (Blob 分离，§3.2)
   │  load/save/exportBackup/importBackup        │
   ▼                                             ▼
idb-keyval customStore (resumex-db)  ←── 同库不同 key（'resumex-state' / 'idb:avatar:<id>'）
```

Electron 差异**只**在 exportBackup/importBackup 的文件系统侧（preload 暴露 `window.resumexBackup.write(file)` / `readDir()` 等），存储层接口不变 —— 这是「Web 与 Electron 共用同一接口」的关键。

### 6.3 关键实现点（成熟可粘贴）

**(a) 导入备份时暂停 persist（防止空 state 覆盖刚导入的数据）**

导入流程：stop persist 写 → 写 Blob（先）→ 写 state.json（后）→ 重新 hydrate/merge → 恢复 persist。项目现状靠「水合门闩 `_hydrated`」实现等价物；完整形态：

```ts
// storageAdapter.setItem 里已带门闩（§2.3），导入时：
// 1) _hydrated = false;            // 关闭 persist 写盘
// 2) await Promise.all([...blob写入, set(STATE_KEY, state, idbStore)]);
// 3) useResumeStore.setState(...); // 直接 setState 进内存（绕过 persist 的 setItem）
// 4) _hydrated = true;             // 恢复
```

**注意**：zustand persist 的 setItem 是**同步排队的**（每次 setState 都触发 setItem），「暂停」必须靠 `storageAdapter` 内部标志（`_hydrated`），没有官方的 `pause()` API。`skipHydration` 只是延迟 watermark，不是暂停写。

**(b) 配额错误抛到 UI（§2.3 已给）**

统一入口：`storage.ts` 的 `isQuotaError` + `useResumeStore.setState({ saveStatus: 'error' })`；blob 写入（saveAvatar）同样 try/catch 并 toast「照片保存失败：存储空间不足」。**测试要点**：Chrome DevTools → Application → Storage → 「Simulate custom storage quota」可模拟低配额（Chrome 88+，web.dev 原文）。

**(c) 照片 Blob 与 JSON 分离（§3.2 已给）**

持久化前把 `ResumeData` 序列化成纯 JSON 时**禁止**带 Blob：partialize 后 JSON.stringify 的对象里 `avatar` 只是 `idb:avatar:<id>` 字符串，模板渲染走 `useAvatarObjectUrl(resumeId)` 的 hook（内部 createObjectURL + useEffect revoke）。

**(d) 备份格式（JSON + 照片分离，zip）**

```ts
// 备份 payload（zip 内两个成员）
// state.json: { state, version, exportedAt }
// avatars/<resumeId>.jpg: blob 二进制（每份 < 150KB）
// 导出：先汇总所有简历的 avatarKey → loadAvatar 拿 Blob → 构造 zip → 下载/写 userData/backups/<时间戳>.zip
// 导入：解 zip → 先写 avatar Blob 到 idb → 再写 state.json（§6.3a 暂停 persist）→ 刷新内存
```

## 7. 调研结论汇总

| # | 问题 | 结论 | 关键证据 URL |
|---|---|---|---|
| 1 | persist 自定义 storage 形状 | `createJSONStorage(() => stateStorage)`，stateStorage 实现 `getItem(name)→string\|null\|Promise`、`setItem(name, value: string)`、`removeItem(name)`；idb `get` 的 `undefined` 要转 `null`。官方警告它不做校验，项目手动 hydrate 校验补足 | zustand src / docs |

| 3 | Blob 分离 | IndexedDB 可直接存 Blob/File（structured clone）；`profile.avatar` 只存 `idb:avatar:<id>`；blob URL 每次现场 createObjectURL、卸载必须 revoke（File API 原文：mapping 存在则 Blob 不可 GC；unload 时全部 revoke） | MDN IDB / IDB-Keyval / FileAPI |
| 4 | IME 防抖 | 序列：compositionstart → (beforeinput → compositionupdate → input)* → compositionend（end 不带 input）。React `onChange` = 原生 input，组合期照常触发、无 isComposing 过滤 → 应用层用 composingRef：组合中只更新 local、不写 store，compositionEnd 重置 debounce | uievents / react docs / ChangeEventPlugin |
